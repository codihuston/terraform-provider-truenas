# truenas_ssh_keypair (Resource)

Manages an SSH key pair in the TrueNAS keychain. A `truenas_ssh_credential` authenticates with a key pair stored here rather than carrying the key itself.

## Example Usage

```terraform
# Generate the key pair with the tls provider so Terraform owns it, and hand the
# private half to TrueNAS. The public half goes in the remote account's
# authorized_keys.
resource "tls_private_key" "backup" {
  algorithm = "ED25519"
}

resource "truenas_ssh_keypair" "backup" {
  name = "backup-host"

  private_key            = tls_private_key.backup.private_key_openssh
  private_key_wo_version = 1
}
```

## Why a separate resource

TrueNAS stores an SSH connection as two linked keychain objects: the key pair
(`SSH_KEY_PAIR`) and the connection that uses it (`SSH_CREDENTIALS`), which
references the key pair by ID. The provider follows that split rather than
hiding the key pair inside `truenas_ssh_credential`, so that one key pair can
back several connections, and so that destroying a connection does not silently
destroy a key other connections still depend on.

## Private keys

`private_key` is a [write-only attribute][write-only]: Terraform sends it to
TrueNAS but never writes it to state. TrueNAS *does* return the private key from
its API, but the provider never reads it back, so the secret exists in the
configuration and on the appliance and nowhere else. A key replaced outside
Terraform produces **no drift**.

Because there is nothing in state to compare against, changing the value in the
configuration is not enough to re-send it. Increment `private_key_wo_version` to
send the current `private_key` on the next apply:

```terraform
resource "truenas_ssh_keypair" "backup" {
  name = "backup-host"

  private_key            = var.backup_private_key
  private_key_wo_version = 2
}
```

Rotating the key changes `public_key`, so the remote account's
`authorized_keys` has to be updated in the same change or the connections using
this key pair stop authenticating.

Write-only attributes require Terraform 1.11 or later.

[write-only]: https://developer.hashicorp.com/terraform/language/resources/ephemeral/write-only

## Generating a key

The provider does not generate keys. TrueNAS can, through
`keychaincredential.generate_ssh_key_pair`, but a key generated by the appliance
has no representation in the configuration and would be replaced on every apply.
Use the [`tls_private_key`][tls] resource, as in the example above, or supply an
existing key.

[tls]: https://registry.terraform.io/providers/hashicorp/tls/latest/docs/resources/private_key

## Deleting

TrueNAS refuses to delete a key pair another object still references. Terraform
destroys a `truenas_ssh_credential` before the `truenas_ssh_keypair` it refers
to, so a pair of managed resources tears down cleanly; a key pair still
referenced by something Terraform does not manage fails the destroy with a
validation error naming the dependency. The provider never passes the API's
`cascade` option, which would delete or disable those dependants instead.

## Import

SSH key pairs can be imported using the keychain credential ID:

```shell
terraform import truenas_ssh_keypair.backup 12
```

`private_key` is write-only, so it is not read during import and no value ends
up in state. `private_key_wo_version` is likewise empty afterwards: set both in
the configuration, and the first apply after the import re-sends the key you
declared. That overwrites whatever key the appliance holds, so make sure the
configured key is the one already installed in the remote `authorized_keys` —
otherwise the connections using this key pair stop authenticating.
